6 ==> 'git init'  ----->  Initialize a new Git repository in the current directory.

7 ==> 'git add file_name'  ----->  Add specific file to the staging area for the next commit.
      'git add *'  ----->  Add all files in the current directory to the staging area for the next commit.

8 ==> 'git commit -m "commit_message"'  ----->  Commit the staged changes with a descriptive message.

9 ==> 'git status'  ----->  Check the status of the Git repository, showing changes and untracked files.

10 ==> 'git push'  ----->  Push the committed changes to a remote repository, such as GitHub. This command uploads your local commits to the remote repository, making them available to others who have access to that repository.

11 ==> 'git pull'  ----->  Fetch and merge changes from a remote repository to your local repository. This command is used to update your local repository with the latest changes from the remote repository, ensuring that you have the most recent version of the code before making further changes or commits.

12 ==> 'git clone repository_url'  ----->  Create a local copy of a remote repository. This command is used to download an entire repository from a remote source, such as GitHub, to your local machine, allowing you to work on the code and make changes locally. 13 ==> >-< 'git log'  ----->  View the commit history of the repository. Gives us the commit_id.
       >-< 'git log -p -2'  ----->  View the commit history with detailed differences for the last 2 commits.
       >-< 'git log --stat'  ----->  View the commit history with a summary of changes for each commit.
       >-< 'git log --pretty=oneline'  ----->  View the commit history in a compact format, showing only the commit ID and message.
       >-< 'git log --pretty=format:"%h - %an, %ar : %s"'  ----->  View the commit history with a custom format, showing the abbreviated commit ID, author name, relative date, and commit message.
       >-< 'git log -S function_name'  ----->  Search for commits that introduced or removed a specific function or keyword in the code. function_name can be in the code like here h1.
       >-< 'git log --grep=commit_message_keyword'  ----->  Search for commits that contain a specific keyword in their commit message.
       >-< 'git log --since=date'  ----->  View commits made after a specific date. date can be in the format "YYYY-MM-DD" or "2 weeks ago", etc.
       >-< 'git log --until=date'  ----->  View commits made before a specific date. date can be in the format "YYYY-MM-DD" or "2 weeks ago", etc.
       >-< 'git log --author="author_name"'  ----->  View commits made by a specific author. author_name can be the name or email of the author.
       >-< 'git log --no-merges'  ----->  View the commit history excluding merge commits, showing only regular commits.

21 ==> If we made any change by mistake and save it then -->
       >-< 'git restore file_name'  ----->  Restore a specific file to its last committed state, discarding any changes made to it.
       >-< 'git restore .'  ----->  Restore all files to their last committed state, discarding any changes made to them.

22 ==> If we added the changes using 'git add' then -->
       >-< 'git restore --staged file_name'  ----->  Unstage a specific file, moving it from the staging area back to the working directory.
       >-< 'git restore --staged .'  ----->  Unstage all files, moving them from the staging area back to the working directory.
       After using 17 we can use 16 to restore the files to their last committed state if needed.

23 ==> Added changes to staging area(didn't commit) after this added more changes to file and save then -->
       >-< 'git restore --worktree file_name'  ----->  Restore a specific file in the working directory to its last committed state, discarding any changes made to it, while keeping the staged changes intact.
       >-< 'git restore --worktree .'  ----->  Restore all files in the working directory to their last committed state, discarding any changes made to them, while keeping the staged changes intact.

24 ==> If we did commit then -->
       >-< 'git reset --soft HEAD^'  ----->  Uncommit and keep the changes.
       >-< 'git reset --hard HEAD^'  ----->  Uncommit, discard, delete the changes and revert back to previous commit so use with caution.

26 ==> >-< 'git tag -a tag_name -m "tag_message"'  ----->  Create an annotated tag with a specific name and message. Annotated tags include additional metadata such as the tagger's name, email, date, and a message describing the tag. A tag is a reference to a specific commit in the Git history, often used to mark important points in the development process, such as releases or milestones. By creating an annotated tag, you can provide more context and information about the tagged commit, making it easier for others to understand the significance of that particular point in the project's history.
       >-< 'git tag'  ----->  List all tags in the repository. This command will display a list of all the tags that have been created in the Git repository, allowing you to see the different versions or milestones that have been marked with tags.
       >-< 'git show tag_name'  ----->  Show the details of a specific tag, including the commit it points to and any associated metadata. 
       >-< 'git tag -a oldcommitmessage oldcommitid'  ----->  To tag old commit in case you forgot. oldcommitmessage is the message given to the old commit and oldcommitid is the commit id of the old commit which we can get from 'git log' command.
       >-< 'git tag -d tag_name'  ----->  Delete a specific tag from the repository.
       >-< 'git push --tags'  ----->  Push all tags to the remote repository on GitHub. This command will upload all the tags that have been created in your local Git repository to the remote repository, making them available for others to see and use.

26 ==> git fork and pull requests -->
       >-< Forking a repository on GitHub creates a copy of the original repository under your GitHub account, allowing you to make changes without affecting the original project. To fork a repository, navigate to the repository you want to fork on GitHub and click the "Fork" button in the upper right corner of the page. After forking, you can clone your forked repository to your local machine using 'git clone' command and make changes to it. Once you have made changes and committed them, you can push those changes to your forked repository on GitHub. Finally, you can create a pull request from your forked repository to the original repository, proposing that your changes be merged into the original project. The maintainers of the original repository will review your pull request and decide whether to merge it or not.

27 ==> gitignore file -->
       >-< A .gitignore file is used to specify files and directories that should be ignored by Git when committing changes to a repository. To create a .gitignore file, simply create a new file named '.gitignore' in the root directory of your Git repository. Then, you can add the names of files or directories that you want Git to ignore, one per line. For example, if you want to ignore all files with the .log extension, you can add "*.log" to the .gitignore file. You can also ignore specific directories by adding their names followed by a slash (e.g., "logs/"). Once you have added the desired patterns to the .gitignore file, save it and commit it to your repository. Git will then ignore any files or directories that match the patterns specified in the .gitignore file when you commit changes to your repository. Here we ignored two files "secrets.json" and "app.log" by putting their name sin the .gitignore file. So when we commit the changes to the repository those two files will not be included in the commit and will not be tracked by Git. This is useful for keeping sensitive information, such as API keys or passwords, out of your Git repository, as well as for excluding files that are generated during development or build processes that do not need to be version controlled.
